## Core doctrine

FashionOS owns the intelligence and workflow. Models/providers/tools are replaceable workers.

Studio Brain is:
- brand-agnostic
- provider-agnostic
- evidence-aware
- preservation-first
- anti-copy
- private in methodology
- governed in learning
- explicit about uncertainty

Client/workspace identity is runtime context only and must not contaminate universal canonical intelligence.

## Creative Organism mental model

Persistent values + knowledge/memory + creative reasoning form the mental center.

Tools/models/Figma/executors are the body/hands.

Required operating loop:
ORIENT -> ATTEND -> FRAME -> RECALL -> DIVERGE -> SIMULATE -> CONSULT -> CRITIQUE -> CONVERGE -> DECIDE -> EXECUTE -> VERIFY -> REFLECT -> LEARN

Learning loop:
OBSERVE -> UNDERSTAND -> DECONSTRUCT -> IMITATE SAFELY -> PRACTICE -> COMPARE -> CRITIQUE -> ABSTRACT -> SYNTHESIZE -> CREATE -> VALIDATE -> REMEMBER

Never learn or reproduce a living creator's signature style. Learn transferable decision principles.

## Product secrecy boundary

Customer UI may show:
- task state
- progress
- confidence where useful
- warnings
- source/rights state
- preservation summary
- approvals
- asset versions
- outputs

Customer UI must not expose:
- repository structure
- provider/model names
- internal prompts
- hidden reasoning
- internal rule IDs
- routing logic/weights
- benchmark internals
- scoring formulas
- learning promotion mechanics
- expert-council debate

## Implementation rules

- Do not silently invent missing product behavior.
- Do not claim a runtime is live unless a real test proves it.
- Do not mark expert profiles ACTIVE until evidence review, contradiction check, anti-copy review, and human validation are complete.
- Do not auto-promote research/practice observations into canonical knowledge.
- Do not let failed preservation outputs pass QC.
- Keep rights/security/source preservation above aesthetics and efficiency.
- Preserve disagreements between experts when materially relevant.
- Keep Figma customer navigation task-oriented.

## Project management discipline

After every meaningful batch:
1. run relevant tests
2. record defects and fixes
3. update `project-management/STATUS.md`
4. update `project-management/BACKLOG.md` if scope changed
5. update `project-management/CODEX-HANDOFF.md` when a decision or milestone materially changes
6. add/refresh QA report when appropriate

Use GitHub history and tests as evidence. Do not rely on memory alone.

## Astra / agent orchestration

If Astra or another agent-orchestration layer is used, it must still treat this repository as canonical context. Agent-generated plans must respect the same value hierarchy, privacy boundary, preservation doctrine, QA gates, and status-update discipline.
